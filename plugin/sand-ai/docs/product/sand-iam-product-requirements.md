# SandIAM 产品需求（平台控制面）

> 状态：已确认的首期需求；SandIAM 是 SandAdmin 宿主插件。2026-08-13 已确认：插件依托宿主运行，不等于应用用户复用宿主后台账号。
> 来源：SandAI 作为多项目 AI 底座时，平台需要把客户/应用/机器身份/服务授权从 AI
> Provider 与业务应用中剥离；产品形态参考 Casdoor 的“组织—应用—身份提供方—权限”
> 控制面，授权判定参考 Casbin 的可配置策略模型。本需求汇总已确认的 SandAI、律序与
> 全量插件边界；不复制或绑定 Casdoor/Casbin 的实现。

## 1. 目标

SandAdmin 是 Sand 平台的宿主；SandIAM 和 SandAI 都以插件形式安装在该宿主中，单独
安装其中任一插件都不构成完整业务能力。SandIAM 是宿主内唯一的接入应用、服务授权和访问
控制面：它让律序等业务应用获得受限的 SandAI 服务能力，而不让它们持有模型供应商密钥或复制
SandAI 配置。

SandIAM 的目标正是以插件方式让项目/应用可以使用自己的用户体系，而不被 SandAdmin 后台账号
体系绑住。宿主初始 `admin` 只用于平台后台的插件安装、配置与全局治理；它不是律序律师、客户
或律所业务管理员的登录身份。SandIAM 提供独立身份目录或身份源绑定、用户类型字典、角色、
策略判定、数据范围与审计等能力；每个应用自行配置其用户类型、业务资源和授权规则。它同时对
application、工作负载客户端和服务动作作出授权判定。

## 2. 首期对象与关系

```text
platform operator
└── organization
    └── application
        └── environment
            └── workload_client
                └── service_grant
                    └── service_action
```

- `organization`：平台客户主体；
- `application`：律序等接入项目，不是其律师/最终用户；
- `environment`：开发、测试、生产的隔离边界；
- `workload_client`：业务后端调用 SandAI 的机器身份；
- `service_action`：例如 `sand_ai.document_parse`，不是 HTTP URL；
- `service_grant`：将动作授给某个环境客户端，并限制 audience、期限、额度、数据等级和网络。

## 3. Casbin / Casdoor 启发与 SandIAM 取舍

SandIAM 不是把 SaiAdmin 的 `BaseLogic::userDataScope()` 抽成另一个插件。后者只围绕
`created_by` 与后台部门/角色做列表过滤，无法覆盖详情、写入、删除、导出、机器身份或跨服务
授权。

| 参考 | 吸收 | 不照搬 |
| --- | --- | --- |
| Casdoor | 平台控制台统一管理组织、平台管理员、接入应用、身份提供方、客户端和审计；应用属于组织，不把客户项目伪装成后台用户。 | 不要求 SandIAM 首期兼容所有 OAuth、SAML、LDAP、SCIM 或社交登录协议。 |
| Casbin | 授权判断以 `主体 + 资源 + 动作 + 领域/属性` 为模型；策略是资源可配置的，不把规则散落在 Controller 或固定字段筛选中。 | 不把 Casbin policy 文本直接当业务数据库或替代 SandIAM 的组织、应用、环境和审计模型。 |
| SaiAdmin 3.x 数据范围 | 认识到“数据范围”是授权的一部分，且必须同时覆盖查询、详情、写入、删除、导出与批量操作。 | 不再以 `created_by` 或后台 `eb_system_*` 关系作为跨项目授权事实来源。 |

首期授权判定至少支持三类主体：

1. **平台后台管理员**：宿主 `admin` 或被委派的后台账号，对插件、平台组织与全局配置的管理权限；
2. **应用人类用户**：例如律序的律师、客户、律所管理员。身份可由 SandIAM 保存或与应用既有身份
   绑定；用户类型字典决定可选角色、默认策略和可操作资源；
3. **工作负载客户端**：对 `sand_ai.document_parse`、`sand_ai.chat.complete` 等语义服务动作的调用权限。

业务应用保留客户、案件、订单、文书和业务流程等实体的最终权威；SandIAM 不把这些业务实体
伪装成 application 或 workload client。律序的律师、客户等应用用户则可由 SandIAM 统一提供
身份与授权能力，见下一节。

### 3.1 两类 SandIAM 使用方式不能混为一谈

1. **律序调用 SandAI（必须）**：律序作为 application，通过 SandIAM 取得工作负载身份与
   service grant，才能调用 SandAI。它解决的是“这个律序部署能否调用哪项 AI 服务”。
2. **应用自身用户与内部授权（SandIAM 通用能力）**：SandIAM 向任何接入应用提供可选的独立
   身份目录、身份源绑定、用户类型字典、角色/API、数据范围、操作授权和审计；律序只是首个
   使用该能力的业务项目。它解决的是“某应用用户能否对某业务资源执行某动作”，并不复用
   SandAdmin 后台账号，也不预设律师、客户或任何业务动作。

第二类接入不改变业务所有权：律序仍保存客户、案件、档案和业务状态；SandWorkflow 仍保存审批
定义、待办和流转状态。SandIAM 保存的是律序用户身份及授权事实，并在每次业务操作时与律序的
案件状态、成员关系及其他业务条件共同校验。SandIAM 的通用需求到此即冻结：用户类型、角色、
资源、动作和策略必须可配置。律师/客户各自能看什么、能做什么，属于律序产品规则；它们由律序
配置为具体策略，不构成 SandIAM 的前置需求或阻塞。

## 4. 必须提供的能力

1. 平台管理员创建、停用并审计 organization、application、environment、workload client；
2. 对 workload client 签发、轮换、撤销短期调用凭证，明文仅展示一次；
3. 注册平台服务及语义 service action，并创建/撤销 grant；
4. 为 SandAI 等服务签发或验证调用上下文，至少包含 application、environment、audience、
   action、有效期、唯一标识及策略/额度摘要；
5. 提供 Adapter 契约，使 SandAI 可验证该上下文和 environment 引用，而不跨库联表或复制
   `sand_iam_*` 数据；
6. 记录身份签发、授权判断、拒绝、轮换与撤销审计；
7. 提供应用用户目录或身份源绑定、用户类型字典、角色/API、数据范围、操作授权与审计能力；
   授权模型至少表达 `主体 + 资源 + 动作 + 领域/属性`，并支持角色授权与属性/范围授权；不复制
   案件/订单/文书等业务实体或业务流程状态。

## 5. 平台管理员与律序委派管理

### 5.1 首期管理方式

- SandIAM 与 SandAI 都依赖 SandAdmin 宿主运行。首期唯一的平台后台最高管理身份为
  SandAdmin 初始库中的 `admin` 超级管理员；该账号不替代 SandIAM 的应用用户目录或律序登录页。
- 开发阶段，平台超级管理员可使用该账号完成律序的 organization、application、environment、
  workload client、服务授权和 SandAI 环境能力配置。经超级管理员明确授权的受控自动化可代为
  执行这些配置，但不得自行创建账号、扩大授权范围或把密钥写入文档、日志。
- 首期由平台完成律序接入后，应交付可复核的接入清单、接口使用说明和基于真实管理页面的图文
  操作手册。页面尚未实现时，不得伪造截图或宣称手册已经可用。

### 5.2 后续律序独立运营

- 平台超级管理员可以在宿主 SandAdmin 中创建后台委派管理员，并授予只作用于律序 organization 的
  SandIAM 与 SandAI 插件权限；也可以在 SandIAM 中为律序创建或绑定律序自身的律所管理员、律师、
  客户等应用用户。二者是不同身份域，不能混用。
- 律序应用管理员可在被平台授予的范围内管理自己的 application、environment、工作负载客户端
  与接口接入配置；是否允许其签发、轮换或撤销本应用的调用凭证和 service grant，必须由平台
  超级管理员逐项授予并留存审计。
- 同一账号可在 SandAI 中配置本应用环境的能力档：为材料整理、检索、文书草拟等业务功能，从
  平台已发布且已授权的模型、模态、解析器和限额选项中选择、测试、发布或回退配置。
- 律序应用管理员不得创建平台 organization、读取其他 organization、注册服务商、读取或修改
  Provider 密钥、创建全局模型、提高额度/数据外发上限，或把未获授的 service action 授给自己。

## 6. 与 SandAI、律序的配置边界

| 配置事项 | 权威方 | 律序应用管理员可做什么 | 不可做什么 |
| --- | --- | --- | --- |
| 平台后台账号、插件菜单与全局治理 | SandAdmin | 使用宿主账号进入被授予的 SandIAM/SandAI 管理入口 | 将后台账号当成律序律师或客户账号 |
| 律序应用用户、用户类型、登录与业务授权 | SandIAM 提供能力；律序负责配置 | 配置律师、客户等用户类型，以及案件等业务资源的策略；律序保存业务实体 | 复用或暴露 SandAdmin 后台账号体系，或把具体业务规则硬编码进 SandIAM |
| 组织、应用、环境、客户端、凭证与服务授权 | SandIAM | 在被委派的律序范围内查看和配置；敏感授权按平台授予的权限执行 | 触及其他组织或扩大自身服务授权 |
| 模型供应商、密钥、可售能力目录与全局安全上限 | SandAI 平台管理员 | 查看本应用可选项及限制 | 读取密钥、注册供应商、创建全局模型或突破上限 |
| 某项律序业务功能实际选择的模型/模态/解析能力 | SandAI 环境能力配置 | 在平台已批准目录内为自己的环境保存、试运行、发布和回退 | 选择未授权能力，或覆盖律序案件权限与数据策略 |
| 律师、律所成员、案件、文件和本地/云端资料状态 | 律序 | 保存实体、案件状态和业务规则；可调用 SandIAM 作授权判断与审计 | 迁入 SandAI 或复制为 SandIAM 的业务实体 |

## 7. 本轮新增验收

- 使用初始 `admin` 超级管理员可为律序完成一次接入配置，所有操作均有审计记录；SandIAM 不另建
  平行超级管理员。
- 创建律序应用管理员后，该账号仅能看到并管理律序 organization 下被授予的资源；访问其他组织
  或平台供应商密钥必须被拒绝并记录审计。
- 律序应用管理员在 SandAI 只能从已发布、已授权的能力目录中为自己的环境选择配置；修改保留
  版本、操作者和回退记录，且不能改变平台设置的额度、数据外发和服务授权上限。
- 律序将来把案件材料提交到云端时，SandIAM 既可提供应用身份与服务授权，也可按律序接入范围
  提供成员/案件的操作和数据范围授权依据；案件实体、文件可见策略和本地备份规则仍由律序最终
  校验，SandAI 不直接浏览律序的全量文件或成员资料。
- 律序不安装、复制或维护第二套 SandIAM。只要律序要使用 SandAI，宿主 SandAdmin 就必须同时
  安装 SandIAM，并为律序登记 application 和服务授权；纯离线且不调用 SandAI 的律序功能不需要
  经过 SandIAM。

## 8. SandAI 集成验收

- SandAI 只消费已验证上下文，并对每个语义 action 二次检查；
- 无 Adapter 返回 `SAND_AI_IDENTITY_CONTEXT_UNAVAILABLE`，无 grant 返回
  `SAND_AI_SERVICE_ACTION_FORBIDDEN`；不得退回旧 API Key、匿名调用或跨库读取；
- SandAI 可配置 Provider、模型、OCR/解析驱动和能力路由，但无权创建 application、
  workload client、credential 或 service grant；
- 律序可调用被授予的 SandAI API；其律师、客户等应用用户可以进入 SandIAM 的身份与授权体系，
  但案件、文书和其他业务实体不迁入 SandIAM。

详细架构与迁移边界见 [SandIAM 与 SandAI 服务接入边界](../architecture/sand-iam-access-boundary.md)。
